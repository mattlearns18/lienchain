# Cowork Handoff — Phase 9 Commit 3 FIX-UP

**Status:** Live QA found critical bugs. Phase 9 ships only after these land.
**Previous commit:** `85ec482` — real Payment txs are submitted, the readiness doc + partial-failure UI scaffolding shipped clean, but the success-detection logic has a hole that would cause silent payment failures to be marked as successful settlements. Mainnet-unsafe as-is.

## The big bug

`src/lib/settle-onchain.js`'s `executeSettlementPayment()` returns `{success: true}` whenever `submitAndWait` returns a hash. It doesn't check whether the transaction actually succeeded on-chain. Result: any `tec*` failure code (e.g. `tecUNFUNDED_PAYMENT`, `tecPATH_DRY`, `tecNO_PERMISSION`) is silently treated as success. The lien is marked `Settled`, `tx2` is populated, the case rolls up to `Settled`, but the clinic received nothing.

**Live reproducer that surfaced this:** Settled a fresh 2-clinic testnet case (`PI-CASE-LIVE-1778724732060`, KC Pain $5K + STL Ortho $7K). Both payments showed validated on-chain and the app marked the case Settled. WebSocket query against XRPL testnet:

```
STL: tx FBB44997 — amount 2,100,000,000 drops — TransactionResult: tecUNFUNDED_PAYMENT
KC:  tx A86FC2CF — amount 1,500,000,000 drops — TransactionResult: tecUNFUNDED_PAYMENT
```

Both transactions failed (`tec*` codes mean the transaction was applied to a ledger but didn't succeed). LienCo's balance dropped by only the fees (~24 drops total), not by the principal. Clinic balances unchanged.

The fix is one line in `executeSettlementPayment` plus the unit issue below.

## Part A — `tesSUCCESS` check

In `src/lib/settle-onchain.js`, after `await client.submitAndWait(signed.tx_blob)`:

```js
const txResult = result.result.meta?.TransactionResult;
if (txResult !== 'tesSUCCESS') {
  return {
    success: false,
    txHash:  result.result.hash,
    error:   `On-chain failure: ${txResult || 'unknown'}`,
  };
}
```

`tesSUCCESS` is the ONLY valid success code in XRPL. Everything else — `tec*` (claims a fee but doesn't apply), `tef*` (preflight failure), `tel*` (local error), `tem*` (malformed), `ter*` (retryable) — is a failure.

Returning `{success: false}` here flows into the existing partial-failure path Claude Code already built in `handleSettled`. The case will be marked `Partial Settlement` and the failed clinic gets a Retry Payout button — Commit 3's partial-failure UI works fine, it just wasn't being triggered for on-chain failures.

## Part B — Amount unit mismatch

`xrpToDrops(amount)` treats `amount` as XRP. The code passes the clinic share **dollar value** (e.g. `2100` for $2,100), which becomes 2,100 XRP — way more than the 100 XRP each testnet wallet holds, hence `tecUNFUNDED_PAYMENT`.

For testnet, scale down so the demo actually flows funds. The point of testnet payments is to show "movement from LienCo to clinic," not to denominate accurately. Scale 1,000:1 so $1 dollar = 0.001 XRP = 1,000 drops:

```js
// Testnet: scale dollar amount to fit faucet-funded wallets.
// For mainnet, this path needs replacement with a stablecoin Amount
// object (e.g. RLUSD / USDC) where 1 unit = $1. See MAINNET-READINESS.md.
const scaleDollarsToXrp = (usd) => xrpToDrops((usd / 1000).toFixed(6));

const tx = {
  TransactionType: 'Payment',
  Account:         wallet.classicAddress,
  Destination:     destinationAddress,
  Amount:          scaleDollarsToXrp(amount),   // TODO(phase10): mainnet currency = issued stablecoin
  Memos:           [/* unchanged */],
};
```

After this scale, $2,100 → 2.1 XRP, $1,500 → 1.5 XRP, comfortably within the 100 XRP balance. The on-chain audit trail still proves the demo flow.

**Add a code comment near this line explicitly noting the testnet-only scaling.** Mainnet path is a separate currency-construction concern flagged in the readiness doc and in this comment.

## Part C — Write `lien.recovery` correctly

In Commit 3's `handleSettled`, on payment success, `lien.recovery` is being written as 0 (or not being written at all — net effect is 0 in storage). The QA case's two settled liens both show `recovery: 0` in localStorage.

`recovery` should be the LienCo dollar share of that clinic's recovery — i.e. `clinic.bill × (clinic.split / 100)` after any pro-rata adjustment from the waterfall. The Commit 1 of Phase 7 already had this wired through correctly; this Commit 3 settlement loop just dropped the field on the floor.

Looking at the data: STL Ortho bill=$7,000, split=70, so LienCo share = $4,900 should be written to `lien.recovery`. KC Pain bill=$5,000, split=70, so $3,500. The exact source-of-truth value is whatever `calcWaterfall` produced for that clinic's `lienCoShare` — same value the on-chain `Amount` is derived from (modulo testnet scaling).

Trace the path in `handleSettled`. Wherever `lien.tx2`, `lien.settledAt`, and `lien.status = 'Settled'` are being written on success, also write `lien.recovery = result.lienCoShareDollars` (or whatever the local variable is named).

## Part D — Success modal "N TXs on XRPL" counter

The animation final step reads "0 TXs on XRPL" even when two transactions were attempted. The counter must read from the success-result list (after the `tesSUCCESS` filter from Part A). Quick fix: count `payoutResults.filter(r => r.success).length` and use that.

If all clinics succeed: "All settlements confirmed — N TXs on XRPL"
If some fail: "Partial settlement — N of M TXs confirmed on XRPL" (or similar). Match whatever the existing partial-failure messaging is.

## Part E — Fiat receipt prefill (rollup from Commit 2 QA)

The Commit 2 fix-up roll-in didn't actually flip the prefill from sum-of-LienCo-shares to `netAvailable`. QA showed prefill is now `12000` (the gross settlement amount input) — different from both the original LienCo-share behavior and the spec'd netAvailable.

Should be `netAvailable` = gross − attorney fee − case costs. For a $12K gross with 33% fee and $0 costs, that's `$8,040`. Mirror whatever the waterfall calculator returns as `netAvailable` — the prefill is just reading from the same memoized waterfall result.

## Part F — Per-clinic retry amount (Claude Code's deviation note)

`handleRetryClinic` uses `bill × (1 - split/100)` (= clinic share fraction) as the retry amount. Sufficient for testnet, but on mainnet this misses pro-rata adjustments from the waterfall (the per-clinic recovery isn't `bill` when net pool < total bills).

Defer this to a Phase 10 polish commit. For now, add a code comment: `// TODO(phase10): retry should re-read from waterfall result, not approximate from bill × split`. Don't fix in this commit — keeps scope contained.
