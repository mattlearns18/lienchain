## Part A — Token validation gate

In the `/attorney/:caseId` route component (probably `src/pages/AttorneyPortal.jsx`), add a token check at the top of the render path. The check applies **only** when the page is rendered via the direct route — NOT when AttorneyPortal-style content is previewed inside the operator dashboard's Attorney View tab.

### Distinguishing direct route from dashboard preview

Use `useLocation()` (react-router-dom) or check `window.location.pathname` at render time:

```js
const location = useLocation();
const isDirectRoute = location.pathname.startsWith('/attorney/');
```

If `isDirectRoute === false`, skip the gate entirely — operator preview renders as today.

### Token check (only when isDirectRoute)

```js
const params = new URLSearchParams(location.search);
const urlToken = params.get('token');

// Find the case (handle both lienchain:cases entries AND legacy single-clinic
// liens where lien.id === caseId via the back-compat shim — see Part D)
const caseRecord = findCaseByCaseId(caseId);
if (!caseRecord) {
  // Case truly doesn't exist (bad caseId in URL)
  return <AccessRequiredPage caseId={caseId} reason="not-found" />;
}

const assignment = caseRecord.attorneyAssignment;
const sessionStore = JSON.parse(localStorage.getItem('lienchain:attorneySessions') || '[]');
const hasValidSession = sessionStore.some(s => s.caseId === caseId);

if (urlToken && assignment && urlToken === assignment.token) {
  // Valid URL token — write acceptedAt (if not already set), persist session
  if (!assignment.acceptedAt) {
    updateCaseAssignment(caseId, { ...assignment, acceptedAt: new Date().toISOString() });
  }
  if (!hasValidSession) {
    sessionStore.push({ caseId, token: urlToken, acceptedAt: new Date().toISOString() });
    localStorage.setItem('lienchain:attorneySessions', JSON.stringify(sessionStore));
  }
  return <FullAttorneyPortal caseId={caseId} />;  // existing render
}

if (hasValidSession) {
  // Previously accepted from this browser, URL token not needed anymore
  return <FullAttorneyPortal caseId={caseId} />;
}

// No URL token, no session → access required
return <AccessRequiredPage caseId={caseId} reason="no-token" />;
```

## Part D — Bug fix: invite generation on legacy single-clinic cases

**Repro:** In Liens tab, click "Invite Attorney" on a seed lien (e.g. `PI-LIEN-2025-11-001` — the KC seed). Modal opens. Pick an attorney. Click Generate Invite. Modal collapses to just the "×" close button — no invite-sent view, no URL displayed. `case.attorneyAssignment` is NOT written.

**Root cause (likely):** the invite write path looks up the case by caseId in `lienchain:cases` and silently fails when the caseId belongs to a legacy single-clinic lien that uses the back-compat shim (`caseId = lien.id`) but never has a corresponding entry in the `lienchain:cases` array.

**Fix:** in the invite write path, if no Case record exists for the caseId, **create a synthetic Case record from the lien data** before writing the assignment. This is consistent with the Phase 5 back-compat shim — same intent, just makes the record real in storage so downstream code that reads `case.attorneyAssignment` finds it.

```js
function ensureCaseRecord(caseId) {
  const cases = JSON.parse(localStorage.getItem('lienchain:cases') || '[]');
  let record = cases.find(c => c.caseId === caseId);
  if (record) return record;

  // No Case record — create synthetic from the lien
  const liens = JSON.parse(localStorage.getItem('lienchain:liens') || '[]');
  const lien = liens.find(l => l.id === caseId) ||
               findSeedLienById(caseId);  // hardcoded mocks live elsewhere
  if (!lien) return null;  // truly unknown caseId

  record = {
    caseId,
    attorney:        lien.attorney || '',
    treatmentMonth:  lien.treatmentMonth || '',
    treatmentYear:   lien.treatmentYear || '',
    clinicLienIds:   [lien.id],
    status:          lien.status === 'Settled' ? 'Settled' : 'Active',
    createdAt:       lien.ts || new Date().toISOString(),
  };
  cases.push(record);
  localStorage.setItem('lienchain:cases', JSON.stringify(cases));
  return record;
}
```

Call `ensureCaseRecord(caseId)` at the top of the invite write path. The rest of the flow continues unchanged.

The seed liens are hardcoded mocks not in `lienchain:liens`. Whatever helper renders them in the Liens tab is the source for `findSeedLienById`. If extracting that's awkward, an alternative is to teach the invite write path to also accept lien-shaped fallback data — same intent, slightly different implementation. Either is fine.
