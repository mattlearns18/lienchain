## Goal

Gate the Settle Now button behind a "Mark Fiat Received" confirmation. The operator records the attorney's fiat wire/check arrival in LienCo's bank account (amount + date + reference + initials) before any settlement TX can fire. Operator-only — the fiat receipt block must NOT appear in the attorney's view of the case (operator-vs-attorney separation rule from CLAUDE.md §4).

Still no on-chain payments in this commit — that's Commit 3. Commit 2 just establishes the receipt-confirmed-before-payout workflow.

## Part A — Data model

New optional field on Case: `fiatReceipt`. Shape:

```js
{
  amount:      number,       // dollars; prefill = sum of LienCo shares across clinics on the case
  receivedAt:  ISO date,     // when fiat arrived in LienCo's bank account
  reference:   string,       // wire confirmation, check number, ACH ref — required
  confirmedBy: string,       // operator name or initials — required
}
```

Stays `null` / `undefined` until the operator marks it received. Persists to `lienchain:cases` (existing localStorage key).

## Part B — Settle Now flow gating

The Settle Now button lives in `AttorneyPreview.jsx`. Today it executes settlement immediately on click. Phase 9 Commit 2 changes:

### When `case.fiatReceipt` is null

- Settle Now button → **disabled**, with a tooltip explaining "Fiat receipt must be confirmed first."
- A new prominent "Mark Fiat Received" button renders above Settle Now. Visually styled like the existing settle button but in a neutral / amber color (not green) so it's clearly a precondition, not the main action.
- Clicking "Mark Fiat Received" opens the receipt modal (Part C).

### When `case.fiatReceipt` exists

- Settle Now button → **enabled** (renders as today).
- Above it, a green confirmation strip:
  ```
  ✓ Fiat received — $X on {date} by {confirmedBy}
  Reference: {reference}
  [ Update ]
  ```
- The Update link re-opens the receipt modal pre-populated with the existing values. Operator can correct an amount/date/reference if needed.

## Part C — Mark Fiat Received modal

Standard modal styled to match the existing AttorneyPreview overlays (`ap-overlay` class pattern).

**Fields:**

| Field | Type | Required | Prefill |
|---|---|---|---|
| Amount Received | number ($) | yes | Sum of LienCo shares across all clinics on the case from the current waterfall result |
| Date Received | date | yes | Today |
| Reference | text | yes | "" — placeholder: "Wire confirmation #, check #, or ACH ref" |
| Confirmed by | text | yes | "" — placeholder: "Your initials or name" |

**Footer:**

- Cancel (closes without saving)
- Save (writes `case.fiatReceipt`, closes modal, re-renders case view)

**Amount mismatch warning (non-blocking):** if the operator enters an Amount Received that differs from the prefilled (computed sum of LienCo shares) by more than $1, show a small yellow note below the input: "Amount differs from expected $X by $Y. Confirm before saving." Don't block submission — real banking can have wire fees, ACH timing, etc. Just surface the discrepancy.

## Part D — Operator-only display rule

The fiat receipt strip and the Mark Fiat Received button MUST NOT appear in the attorney's view of the case. The attorney's view is rendered when:

- The page is at `/attorney/:caseId` (direct route) and the token gate from Phase 8 passed
- OR the page is at `/attorney/demo` (the standalone demo route)

The operator's view is rendered when:

- The page is inside the operator dashboard's Attorney View tab (no route change — rendered via `Dashboard.jsx`)

`AttorneyPreview.jsx` is shared between contexts. Add a prop `isOperatorView` (boolean, defaults false) that the component checks before rendering fiat-receipt UI. The Dashboard's Attorney View tab passes `isOperatorView={true}` to AttorneyPreview. The direct `/attorney/:caseId` route does not pass this prop (so it defaults false), and `/attorney/demo` likewise.

This mirrors how the existing operator-vs-attorney separation is enforced for the waterfall (see CLAUDE.md §4 — the waterfall math fields appear in operator preview but not in any operator-side production tab).

## Acceptance criteria

1. Open the operator dashboard, switch to Attorney View tab, select a case with no fiat receipt. The Settle Now button is **disabled** with a tooltip. A "Mark Fiat Received" button renders above it.
2. Click Mark Fiat Received → modal opens with Amount prefilled to the sum of LienCo shares (e.g., $9,614.50 for the QA case), Date prefilled to today, Reference + Confirmed by empty.
3. Submit with valid inputs → modal closes, the green confirmation strip renders above Settle Now showing the saved values, Settle Now is now enabled.
4. Click Update on the strip → modal re-opens with the saved values prefilled.
5. Enter an Amount that differs from prefill by >$1 → yellow mismatch note appears below the input, but Save still works.
6. `case.fiatReceipt` is persisted to localStorage with all four fields after save. Reload — receipt strip still shows.
7. Open the same case via `/attorney/:caseId?token=...` (direct route, attorney view). The fiat receipt strip and Mark Fiat Received button **do not appear**. Settle Now is shown as today (the gate is operator-side only — though see note below on whether attorneys should be able to settle at all).
8. `npm run build` clean. No console errors.

## Note on attorney-side settle button behavior

Today the Settle Now button is visible to attorneys when they access a case via `/attorney/:caseId`. In the real-world Phase 9 flow, the attorney shouldn't actually be executing the on-chain payouts — only LienCo's operator does that, after confirming fiat receipt. But the demo expectation may differ.

**For this commit:** preserve current behavior on the attorney side — Settle Now renders the same as today on `/attorney/:caseId`, no fiat-receipt gate. The gate only applies in the operator's Attorney View tab. If Matt wants to hide Settle Now entirely on the attorney side, that's a separate ask — flag in result file if you have a strong opinion either way.
